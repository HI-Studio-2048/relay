# Recatch (the repo is still called relay)

Social DM automation: comment to DM, flows, a shared inbox, broadcasts, CRM and Claude-powered replies. One process serves the web UI, the webhooks and the worker. `README.md` covers features and setup. `INTEGRATIONS.md` is the handover document for every platform: what is live, what is waiting and on whom, where each account lives, and the order to resume in. Keep it current as you work.

## Names

The product is Recatch (renamed from Relay). User-facing text says Recatch. Keep the old name wherever something already deployed or integrated depends on it: the repo and Railway project, the `relay_session` cookie, the `rly_` API key prefix, the `X-Relay-Signature` webhook header and the `relay` key in exported flow files.

## Commands

- `npm run dev` serves on port 43173. Without `DATABASE_URL` and `REDIS_URL` it uses PGlite under `.data/` and an in-memory queue, which is enough for the UI and tests.
- `npm test`, `npx tsc --noEmit` and `npm run build` should all pass before anything is pushed.
- The person you work with is on Windows. Any command you ask them to run has to be for PowerShell (say so, and say the folder). Never hand them bash or Unix-only commands.

## Deploying

Railway deploys every push to `main`, which takes five to six minutes (the old build keeps serving until the new one is up, so a change is not live the moment a deploy shows as started). Live at https://recatch.app (the old `relay-production-71da.up.railway.app` address still works). `GET /api/health` reports the service and database state.

Environment variables live in Railway and never in the repo or in chat. `.env.example` and the table in `README.md` list the names.

`proxy.ts` answers every signed-out `/api/*` request with 401, route or not, so a 401 does not prove a new route is deployed. Check from a signed-in browser instead. After a push, run `railway deployment list --service recatch` too: the CLI is linked to the production project, and a failed build keeps the old one serving. `railway logs --build --service recatch <deployment id>` shows why it failed. If the CLI asks to be linked, run `railway link --project f59f9253-d69f-425f-8d00-698eb7b2a2f2 --environment production --service recatch`. Runtime logs only cover the current deployment, so pass an older deployment id to read what happened before a redeploy.

More than one person pushes straight to `main`. At the start of a session, read `git log` for commits you haven't seen, and compare the variable names in `railway variables --service recatch --kv` with `.env.example`: code that needs a variable nobody set has shipped before (the Stripe paywall went live without its keys).

## Things that have bitten before

- This is a recent Next.js with breaking changes. Read the guide in `node_modules/next/dist/docs/` before using an API you are not sure of (see `AGENTS.md`).
- A route file may only export HTTP handlers and route config. Put shared constants in `src/lib/`. Sibling dynamic segments must share one name, so use a static segment like `item/[id]` when a second route would clash.
- A new table goes in two places: `src/lib/db/schema.ts` and the migration SQL in `src/lib/db/sql.ts`. `schema-sql.test.ts` fails when they disagree.
- Railway installs with `npm ci` on node 22 (npm 10.9.9), which refuses a lock file written by a newer npm that is missing optional entries (it failed on `@emnapi/runtime`). After adding or changing a dependency, run `npx npm@10.9.9 install --package-lock-only --ignore-scripts`, then check `npx npm@10.9.9 ci --dry-run --ignore-scripts` prints no `Missing`. A failed deploy keeps the old build serving, so check `railway deployment list --service recatch` rather than assuming a push went live.
- Pages and routes reachable while signed out are listed in `src/proxy.ts`. An entry matches the whole path or whatever sits under it after a slash, so a file with an extension (`client-metadata.json`) needs its full name listed. `src/proxy.test.ts` goes through the real proxy; route tests that call a handler directly skip it and cannot catch a missing entry.
- Tests that need the database change into a temp directory before the first `getDb()`, mock `@/lib/auth` for `requireUserId`, and stub `fetch` for providers. They never call real services. `src/lib/oauth/oauth.integration.test.ts` is the pattern to copy. Start the database in `beforeAll` (`await getDb()`), not in the first test: setup gets 30 seconds and a test 20, and a busy full run timed out three suites that started it inside a test. Routes that call `requireBotAccess` need it mocked too, because the real one calls `requireUserId` inside its own module, where the mock does not reach.
- The working tree uses CRLF line endings. A script that edits files should keep the file's existing endings.
- Vitest allows 20 seconds per test and 30 for setup, because integration suites load big libraries and start a database while many run at once. `broadcast A/B split` is slow (about a second alone). If something still times out, rerun it by itself before treating the failure as real.
- Slack read methods such as `users.info` only accept form-encoded parameters. JSON is for `chat.*`. A fake that accepts both hides the bug.
- A Discord DM carries no server, so the shared bot cannot tell which customer a DM is for. People run `/chat` in the server, and `discord_routes` remembers it. Never let two connections hold the same bot token, or every DM is answered twice.
- Bluesky's `bsky.social` is only the sign-in entryway. Chat calls must go to the account's own server (in the sign-in response), or they answer Method Not Implemented. Notifications go through the same server with the app view proxy header (`did:web:api.bsky.app#bsky_appview`).
- The server runs as `next start --hostname 0.0.0.0`, so `request.url` has the origin `http://0.0.0.0:PORT`. Never build a redirect from it: a form POST that redirects that way sends the browser to a dead address after the work already happened (the broadcast confirm did exactly this). Use `redirectTo()` from `src/lib/http.ts`, which sends a relative `Location`. Absolute URLs handed to a provider (OAuth redirect URIs, webhook URLs) come from `publicUrl()`, which reads `PUBLIC_URL`.
- Never put a raw `Date` into a drizzle `sql` template. The Postgres driver on Railway rejects it, while PGlite accepts it, so tests pass and the page crashes live (the All accounts page did). Pass `date.toISOString()` with a `::timestamptz` cast, or use `gte()` and friends on the column.
- Zernio is back, for Instagram, Messenger and WhatsApp only, and only as one company key (`ZERNIO_API_KEY`) with one profile per Recatch user (profile `externalId` = user id). Never take a key a customer pasted, and never list Zernio accounts without a `profileId`: the company key can see every customer's accounts. The webhook is a single URL, `/api/zernio/webhook`, signed with `ZERNIO_WEBHOOK_SECRET`, and finds the customer from `profiles[].externalId`, `profile` or `account.profileId`. Zernio returns an account's `profileId` as an object (`{ _id, name, externalId }`), not a string, and the connect callback carries the platform but no `accountId`. Both broke the first real Instagram connect, so never compare `profileId` as a string and never trust the callback address; read the accounts back from Zernio. Comment to DM, moderation and public replies run through it. Other networks stay direct or greyed out; do not add them through Zernio.
- TikTok's sandbox only lets approved target users sign in (Sandbox settings, Target users). Anyone else gets `non_sandbox_target` on TikTok's screen, which looks like a bug and is not. The sandbox keys are the ones in Railway until the production review passes. Do not swap in production keys early.
- Google's branding check wants the home page domain verified in Search Console under the same account that owns the Cloud project (a DNS TXT record on the root in Cloudflare). Without it the consent screen verification fails with "home page is not registered to you".
- Pages that read an environment variable at request time need `export const dynamic = "force-dynamic"`, or the build bakes in the value it saw.
- Console pages copy their server data into state (`useState(props)`), so switching accounts would leave the old account's data on screen. `src/app/(console)/layout.tsx` keys the page area on the selected account so every page remounts. Before that fix, the Flows list showed one account while New flow saved to another.
- Uploads and received media live in Postgres (`media_files`), not on disk: the container disk is wiped on every deploy, and production had lost every upload. `src/lib/media.ts` still reads old files from `MEDIA_DIR` if a volume ever kept any.
- A push restarts the server when the deploy switches over, which cuts off any long request in flight (a Missed comments send, for one). Don't push while someone is sending.
- The flow editor sends the flow's `updated_at` it loaded (`baseUpdatedAt`) with every save, and the route refuses a stale one with 409 (`src/lib/flow-version.ts`), so a tab opened before a change can no longer overwrite it. Callers that send no version (`/api/v1`, the agent, imports) are not checked. A fix made by hand in the database must bump `updated_at`, or open tabs won't notice it.
- Railway settings (builder, healthcheck) live on the service itself. `railway.toml` was removed on 2026-10-19 because Config as Code ends on 2026-12-01, and the start command is Railpack's default `npm run start`. Railway's TypeScript config (`.railway/railway.ts`) would need the `railway` npm package and isn't used.
- Changing live data by hand: do it through `railway ssh` with the `postgres` package, in a transaction, and for a flow put the old row in `flow_versions` first so it can be restored from the editor's History.

## Where things are

- `src/lib/channels/catalog.ts` is the list the Channels page shows: live channels, ones that connect with the customer's own Meta app, and greyed-out ones still to come. Change a channel's state there when it changes in `INTEGRATIONS.md`. Connect buttons open `/setup?channel=<id>`.
- `src/lib/channels/`: one adapter per messaging channel (Telegram, Meta, WhatsApp, Discord, Slack, Bluesky). `index.ts` dispatches sends and inbound parsing. `src/lib/webhook.ts` runs every inbound event through the flow engine.
- The design rule for a new channel: customers connect with one click through an app the company owns (Add to Slack, Add to Discord, Sign in with Bluesky), and pasting their own token is only the fallback. Telegram is the exception because it has no company-wide API. Each platform's company app, its variables and its gotchas are in `INTEGRATIONS.md`.
- Slack: `slack.ts` (send, parse, signatures), `slack-install.ts` (OAuth), `slack-webhook.ts` (one handler shared by the per-app URL and the shared `/api/slack/events`). Bluesky: `bluesky.ts` (chat calls, polling log), `bluesky-manager.ts` (the poller, started from `startup.ts`), `bluesky-oauth.ts` (Bluesky's OAuth client, settings and the encrypted session store). Shared Discord bot: `discord-install.ts`, `discord-shared.ts`.
- Discord is different from the others: it delivers DMs over a persistent websocket, not a webhook. `discord-gateway.ts` is the connection (heartbeat, resume, backoff), and `discord-manager.ts` keeps one per connected bot and re-syncs every minute from `startup.ts`, and skips servers added through Add to Discord, which share the one bot held by `discord-shared.ts`. Run only one instance with the worker on, or every DM is answered twice. The Bluesky poller has the same single-instance rule.
- YouTube is a comments channel built on the Google connection: signing in makes a `youtube` row in `bots` that points at the connection (`settings.youtubeConnectionId`), `youtube.ts` is the adapter and `youtube-manager.ts` polls comments every two minutes (single instance, like Bluesky). YouTube has no DMs, so `sendYouTubeReply` only posts replies a person wrote (source `agent`) and refuses broadcasts and follow-ups, which would otherwise land in public. Google reviews the scope against a demo video of the real feature, so a new YouTube call needs to show up in that video. Confirmed live on 2026-10-16 (automatic reply and hold for review on the company channel). Google verified the app on 2026-10-19 and the consent screen is In production, so anyone can connect. Comment moderation (Starters & hours) shows for Meta and YouTube accounts; on YouTube a match is held for review, never hidden, and stays visible to its own author.
- `src/lib/oauth/` and `src/app/api/connections/`: Connected apps (TikTok, and the Google sign-in behind YouTube). These are sign-in and read connections, not messaging channels. To add a provider, add its config in `providers.ts`, its env keys, and tests. Anything that calls a provider's API gets its token from `getAccessToken`, never from the database directly.
- AI: `src/lib/ai.ts` is the one place that calls a model (`parse()`), and every AI feature goes through it. An account can save its own OpenRouter key and model on the AI assistant page (`ai-provider.ts`, `src/app/api/bots/[id]/openrouter/`, `components/openrouter-card.tsx`). The key is encrypted in `bots.settings.openrouter`, apart from `settings.ai`, so the settings the browser reads never carry it. With a key, calls go to OpenRouter; without one they use the server's `ANTHROPIC_API_KEY`. Anything new that calls `ai.ts` must pass `provider: readAiProvider(bot.settings)` or that account's key is ignored and the call quietly bills the server key. `aiConfigured(provider)` is per account. The Instructions box (`settings.ai.instructions`) is added to prompts through `rulesBlock()`.
- Email: `src/lib/email.ts` sends through Amazon SES with a hand-written SigV4 signer over fetch (no AWS SDK, so no lockfile changes). It needs `AWS_SES_ACCESS_KEY_ID`, `AWS_SES_SECRET_ACCESS_KEY`, `AWS_SES_REGION` and `EMAIL_FROM` together, and is off otherwise. `sendEmail` returns false instead of throwing. Used for password reset (`auth/reset.ts` signs a link that carries a fingerprint of the current password hash, so it dies when the password changes and needs no table), the signup welcome email, and `owner-email.ts` (hand-off alert to the account owner). Keep email to those few, because a flood from one account would hurt the sender's SES reputation. Confirmed working on 2026-10-14: `recatch.app` is verified in SES `us-east-1` (Easy DKIM, MAIL FROM `mail.recatch.app`, DMARC `p=none`, records in Cloudflare) and the account is out of the sandbox. The SES account is shared with the company's other projects, so their volume shows on the dashboard and a bad bounce rate here would hurt them too. Bounces and complaints: SES publishes them to an SNS topic, SNS posts to `/api/email/feedback`, and hard bounces and complaints land in `email_suppressions`, which `sendEmail` checks first (`email-feedback.ts`). The route only accepts the topic named in `AWS_SES_SNS_TOPIC_ARN`, because any AWS account can make a topic SNS signs validly. Soft bounces are left to SES. The AWS side has been live since 2026-10-15: a Standard topic in `us-east-1`, SES feedback for `recatch.app` pointed at it, and an HTTPS subscription the route confirmed by itself. If the topic ever changes, set the new ARN and wait for the deploy before subscribing, or the confirmation is refused.
- Billing: `src/lib/billing/`. Recatch is paid, and `users.billing_status` decides access (`access.ts` is the one place the rules live). `past_due` keeps the workspace open while Stripe retries; `unpaid` and `canceled` close it and pause the account's automations: `paused.ts` stops inbound processing, every send in `sendChannelReply`, queued broadcasts and the `/api/v1` keys. `none` (never paid) is not paused, because it can't get past the login, and test accounts start there. Stripe can deliver events out of order and for an old or duplicate subscription, so `webhook.ts` ignores `incomplete` style statuses and events for a subscription other than the live one on file. Checkout expires any open session and refuses while a subscription is live, so nobody pays twice. Stripe is in live mode since 2026-10-19, on Recatch's own Stripe account (a restricted `rk_live_` key and the live webhook secret are in Railway). The webhook is built against API version `2026-09-30.endive`, pinned in `stripe-api.ts`; a new Stripe endpoint must use the same version, or invoice payloads change shape. To test, use the sandbox inside that Stripe account with its own key and webhook, never the live one.
- The Overview growth agent (`src/lib/agent/`) only saves drafts. Its key comes from `agent/provider.ts` (the login's newest OpenRouter key, otherwise the server key) and `/api/agent/chat` is capped at 30 an hour per login.
- Console scope (`src/lib/scope.ts`): only Overview and Live Chat can show All channels (`isAggregatePath`). Every other page works on one account and the switcher names it. The flow editor pins the switcher to the flow's own account (`PinnedBot`).
- Comment flows on Meta accounts have a Missed comments panel (`src/lib/comment-catch-up.ts`, `src/app/api/flows/[id]/missed-comments/`, `components/flow-canvas/missed-comments.tsx`). It lists a post's comments from Zernio and runs the ones a flow missed through the normal comment path with `catchUp` set on the inbound event: DM only, no public reply, no hiding, no second inbox line. Instagram allows a private reply for 7 days after the comment. Nothing is sent until a person clicks Send.
- Live Chat shows and sends images, GIFs and files. Incoming attachments arrive on `NormalizedInbound.attachments` (only Zernio fills it so far), `webhook.ts` saves a copy, and `messages.media` holds them. The reply route only accepts files uploaded to Recatch.
- `src/app/(marketing)/`: the public site, including the privacy, terms and data deletion pages that every platform application asks for.

## Looking at the live database

The Railway Postgres is only reachable from inside Railway (`postgres.railway.internal`), and there is no public URL. To run a query, link the CLI to the `recatch.app` project (production) and run it from the service: `railway ssh --service recatch -- node -e "..."` using `require("postgres")` and `process.env.DATABASE_URL`. Nothing prints a secret that way. Start read-only.

Accounts are rows in `users`. Connected channel accounts (`bots`) belong to a user through `owner_id`, and the app only shows a login its own bots. Rows from before logins existed have a null `owner_id`, so they are invisible to everyone until someone assigns them (`update bots set owner_id = <user id> where id = <bot id> and owner_id is null`). Contacts, flows and messages hang off the bot, so they follow it. If someone says an account or its data is missing, check for bots with a null owner first.

## Meta through Zernio

Instagram, Messenger and WhatsApp connect through Zernio's hosted flow, wired in `src/lib/zernio-connect.ts`, `src/lib/channels/zernio.ts` and `src/app/api/zernio/`. It needs `ZERNIO_API_KEY` and `ZERNIO_WEBHOOK_SECRET` in Railway (both are set) and one webhook registered in Zernio. The fake Zernio in `src/lib/zernio.integration.test.ts` now mirrors the real response shapes. Instagram is confirmed live since 2026-10-15: `@danielphilipwatch` connects and saves, its DMs and comments land in Live Chat, and real photos and GIFs show there (2026-10-19). It is running a giveaway until October 31st, so treat its flows as live customer data. Instagram refuses a private reply whose button link is not a real URL, and the engine marks a commenter "answered" before the DM goes out; a refused DM now takes that mark back (`unmarkAnswered` in `webhook.ts`), so Missed comments can still offer them. WhatsApp and Messenger are still untested live. `INTEGRATIONS.md` has the open checks under "Pick up here". Zernio bills the company per connected account, which is why deleting a Meta account in Recatch disconnects its accounts and drops the profile.

## Platform applications

The developer apps (Google, Pinterest, TikTok, Meta, Slack, Discord) belong to the company admin account, not to anyone's personal login. Client secrets, passwords and tokens are entered into Railway by a person and are not read or written anywhere else. Claude's permission settings block writing to a secret store, so give the person a PowerShell command to run. Bluesky's signing key is made by `scripts/bluesky-keygen.mjs` and piped into Railway with `--stdin`, so it never shows on screen. Meta's account checks, CAPTCHAs and any consent given on someone's own account are done by that person. Status of each review lives in `INTEGRATIONS.md` (TikTok submitted 2026-10-14 and still pending; YouTube verified 2026-10-19; Pinterest trial still pending). Platform review forms often want a demo video of the working flow, so build and test the connection in Recatch before applying. Every requested scope needs a user-facing feature the video can show; YouTube was sent back once because sign-in plus a channel name was all Recatch did with `youtube.readonly`. TikTok's production form does not keep a draft, so set things up in its sandbox first.
